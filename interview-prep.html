What differentiates it from existing solutions? Differentiation

Zero-config start with SQLite — works out of the box without Docker or database setup. Most alternatives (Nextcloud, Seafile) require significant infrastructure.

Auto-fallback database — if PostgreSQL is configured but unreachable, it silently falls back to SQLite and the app always starts.

Per-role speed throttling — upload and download bandwidth limits per role, not just storage quotas. Most OSS solutions don't have this.

Full theme customization — not just light/dark, but every color variable is editable with live preview and JSON export/import.

Modern React frontend — drag-and-drop upload queue, live polling dashboard, responsive design, not a server-rendered PHP app.

What feature are you most proud of? Strength

The file sharing system — it's surprisingly comprehensive for a solo project. Public links, password protection, expiration timers, one-time downloads, preview/download toggles, instant revocation, and full audit logging of every share event. The token generation uses secrets.token_urlsafe for cryptographically secure random tokens.

What was the hardest feature to implement? Strength

Soft delete with trash restoration. It sounds simple but requires:

1. Moving physical files to a trash directory while keeping database records intact.
2. Managing the DELETED system tag to filter views correctly (this was actually a subtle bug where missing tags caused all files to appear in trash).
3. Handling foreign key constraints when permanently deleting — ShareLinks and FileVersions must be cleaned up before the File record can be removed.
4. Adjusting storage quotas since trashed files don't count toward usage.

What feature took the longest?

The React frontend overall. Specifically: the upload queue with drag-and-drop, progress tracking, and the floating indicator that snaps to corners. Building a stateful upload context that tracks multiple concurrent uploads, communicates with the backend, and updates the dashboard when uploads finish took significant iteration.

What would you redesign today? Future

I'd replace the HTTP polling with WebSockets or Server-Sent Events for live dashboard updates. Polling every 15 seconds (5 during uploads) is simple but wasteful. WebSockets would push updates only when something actually changes.

I'd also refactor file storage behind an abstraction layer so S3/MinIO/object storage backends could be swapped in without touching every route that reads or writes files.

What features did you intentionally avoid?

Real-time collaboration on files, collaborative editing (like Google Docs), and federated sharing between instances. These would dramatically increase scope. I focused on single-tenant personal/small-team storage.

I also avoided client-side encryption because key management for non-technical users is genuinely hard — lose your key, lose your files. I'd rather implement server-side encryption at rest with a managed master key.

What compromises did you make? Weakness

SQLite for default — great for simplicity but causes locking issues under concurrent writes. The auto-fallback is a compromise between usability and scalability.

Polling instead of WebSockets — simpler to implement, works through firewalls, but less efficient and higher latency for updates.

No antivirus scanning — dangerous extensions are blocked but actual malware scanning is absent. ClamAV integration would be the right next step.

How did the project evolve over time?

Started as a basic Flask file upload/download app. Added user authentication, then moved to React for the frontend. Multi-user support with roles came next, then the sharing system, then trash/versioning. The theme system and notes were later additions. Each phase uncovered bugs in previous assumptions (like the foreign key cascade issues when deleting users or files).

What did users/testers struggle with most?

Two things: CSRF token errors when cookies were stale or sessions expired, and the dashboard not updating after uploads without a manual refresh. The latter led to the live polling and silent background refresh features. The former led to better error handling in the frontend and clearer messaging.

What feedback changed your design?

The trash system was originally going to be a simple boolean is_deleted flag. But testing showed users expected to restore files, see when they were deleted, and have automatic cleanup. That led to the separate TrashedFile model with timestamps and retention scheduling.

What would version 2 include? Future

WebSocket live updates, resumable/chunked uploads, S3 backend support, 2FA, ClamAV scanning, encryption at rest, and a proper admin mobile view. Maybe a desktop sync client using the existing REST API.

2. Architecture ▼
Why did you choose Flask? Strength

Flask is lightweight, explicit, and has a massive ecosystem. For a project where I needed to understand every layer of the stack, Flask's "start simple, add what you need" philosophy was perfect. I could reason about every request lifecycle, every middleware, and every extension. It also made the app factory pattern and blueprint organization very clean.

Why not Django/FastAPI?

Django would have been overkill — I didn't need the admin panel, forms framework, or ORM opinions. I wanted full control over SQLAlchemy model definitions and migration strategy.

FastAPI is great for APIs but the project needed server-rendered pages (auth, admin, share links) alongside the React SPA. Flask's Jinja2 integration and mature extension ecosystem (Flask-Login, Flask-WTF, Flask-Mail) handled both worlds better than FastAPI at the time.

Why React for the frontend?

The dashboard needed rich interactivity: drag-and-drop uploads, live progress bars, modal dialogs, theme switching, and a responsive file grid. Server-rendered templates would have required jQuery or vanilla JS sprinkles that become unmaintainable. React's component model and context API let me build a clean state architecture.

Why SQLite as default? Strength

Zero configuration — no database server to install, no connection strings, no Docker. A user can clone the repo, run pip install, and it works. For personal NAS use cases (1–3 users), SQLite is perfectly adequate. The auto-fallback to SQLite when PostgreSQL is unreachable means the app is resilient and always starts.

Why support PostgreSQL/MySQL?

SQLite doesn't handle concurrent writes well. For multi-user production deployments, PostgreSQL is the right choice — better concurrency, full-text search potential, and backup tools. MySQL support was added because some enterprise environments standardize on it. Both are supported through SQLAlchemy's unified ORM layer with connection string parsing in config.py.

How is your app structured internally?

Standard Flask blueprint architecture:

app/
  __init__.py        — App factory, extensions, blueprint registration
  config.py          — Reads .env, handles database fallback logic
  models.py          — SQLAlchemy models (~20 tables)
  forms.py           — WTForms
  routes/            — Blueprints: auth, files, admin, trash, share, etc.
  utils/             — Utilities: security, email, scheduler, rate limiting
frontend/
  src/components/    — 23 React components
  src/context/       — 5 context providers (Auth, Theme, Upload, Modal, CSRF)
Why separate routes/utils/models?

Models define the data layer — they shouldn't know about HTTP or rendering.
Routes handle HTTP concerns — request parsing, auth checks, response formatting. They orchestrate models and utils.
Utils encapsulate reusable logic — email, rate limiting, file streaming — so routes stay readable and testable.

This separation makes it easy to find where things live and prevents circular imports.

How does the app initialize?

run.py calls the app factory in app/__init__.py. The factory:

1. Creates the Flask instance
2. Loads config from Config class (reads .env, handles database fallback)
3. Initializes extensions (SQLAlchemy, LoginManager, Mail, CSRFProtect, Migrate)
4. Registers blueprints (auth, files, admin, etc.)
5. Creates directories (files, logs, instance)
6. Starts the background scheduler
7. Cleans up orphaned user directories from the filesystem

Explain your app factory pattern.

The app factory is a function (create_app() in app/__init__.py) that returns a configured Flask instance rather than creating it at module import time. This enables:

1. Testing — create app instances with different config (test DB, debug mode).
2. Multiple instances — though not used here, the pattern supports it.
3. Lazy initialization — extensions are bound to the app after creation, avoiding circular import issues.

How do frontend and backend communicate?

REST API over HTTP/JSON. The React frontend makes fetch calls to Flask endpoints. CSRF tokens are fetched at startup and included in every mutating request (POST/PUT/DELETE). The backend serves the built React app as static files from app/static/react/ and handles API calls at /api/* and /* routes.

How do you organize API endpoints?

Grouped by domain under blueprints: /auth/* for auth, /files/* for file ops, /admin/* for admin, /api/notes for notes, /api/trash/* for trash. Internal utility routes don't expose JSON — they render templates for share links and legacy views.

How do you manage shared state in React?

Five React Context providers:

AuthContext — current user, login/logout, role checks
ThemeContext — current theme colors, dark/light mode, localStorage persistence
UploadContext — active uploads, progress tracking, queue management
ModalContext — global modal/dialog management
CSRFContext — CSRF token fetch and refresh

For a project this size, Context + useReducer is sufficient. No Redux/Zustand needed.

How do you handle configuration management?

Centralized Config class in app/config.py reads from environment variables with sensible defaults. It also handles database URL validation, directory initialization, and file category mapping. Environment-specific overrides (like FLASK_DEBUG) are checked at runtime. This keeps secrets out of code and makes the app deployable anywhere.

Why use environment variables?

Security (secrets aren't in source control), portability (same code runs on different machines with different config), and 12-Factor App compliance. The .env file is loaded by python-dotenv and ignored by git.

How would you split this into microservices?

Natural boundaries: Auth service (user management, sessions, roles), File service (upload, download, storage, quotas), Share service (link generation, public access), Notification service (emails, activity feed). Each would have its own database (or shared with event sourcing). An API gateway would handle routing and auth verification.

Why didn't you use microservices?

Single-tenant personal/small-team use case. A monolith is simpler to deploy, debug, and reason about. Microservices add network latency, deployment complexity, and operational overhead that isn't justified until you have multiple teams or need independent scaling of subsystems.

How would you scale the architecture?

Immediate: move to PostgreSQL, run behind Nginx with Gunicorn multi-workers, add Redis for session storage so multiple app instances share state. Medium-term: extract file storage to S3/MinIO, add CDN for static assets and file delivery, implement async task queue (Celery + Redis) for emails and file processing. Long-term: microservices if the team grows.

3. Authentication & Security ▼
How are passwords stored? Strength

bcrypt with automatic fallback for legacy hashes. On login, if a user has a PBKDF2 hash (from an earlier version), the password is verified against it, then transparently rehashed with bcrypt and saved. New passwords always use bcrypt.

Why bcrypt? Strength

bcrypt is adaptive (work factor can be increased as hardware improves), salts automatically, and is resistant to GPU/ASIC attacks because it uses memory-hard Blowfish cipher. It's also the modern standard — Django, Flask-Security, and most frameworks default to it.

Why migrate from PBKDF2?

PBKDF2 is vulnerable to GPU acceleration because it uses SHA-256 which is fast in hardware. bcrypt's memory requirements make parallel attacks much harder. The migration happened transparently — no password reset required for existing users.

How do sessions work?

Flask-Login manages user sessions with server-side session storage (signed cookies by default). Cookies are HTTPOnly, SameSite=Lax, and Secure can be enabled via SESSION_COOKIE_SECURE env variable. Session duration is configurable. The session cookie contains a signed user ID; the actual user object is loaded from the database on each request via the @login_required decorator.

Why cookies instead of JWT?

Cookies with server-side sessions are simpler and safer for a traditional web app. JWTs are stateless which means you can't revoke them server-side without a denylist (which reintroduces state). With cookies, I can invalidate a session instantly by removing it from the server. CSRF protection is also mature and well-understood for cookie-based auth.

How do you prevent CSRF? Strength

Flask-WTF's CSRFProtect extension validates tokens on every mutating request. The frontend fetches a CSRF token at startup via /auth/api/csrf-token and includes it in the X-CSRF-Token header for all POST/PUT/DELETE requests. Tokens are time-limited and cryptographically random.

How do you prevent brute-force attacks? Strength

Multi-layered approach:

1. Rate limiting — per-IP request throttling via custom middleware. Login endpoints have stricter limits.
2. IP blocking — repeated failed login attempts trigger automatic IP blocking with exponential backoff.
3. Account lockout — too many failures on a single account locks it temporarily.
4. Logging — every failed attempt is logged with IP, username, and timestamp.

Explain your rate limiting.

Custom RateLimiter class tracks requests per IP in memory with sliding windows. Standard endpoints: 100 requests/minute. Login endpoints: 5 attempts/minute with progressive penalties. The limiter uses a cleanup thread to prevent unbounded memory growth from stale entries.

How does IP blocking work?

The security_utils.py module maintains a blocked-IP dictionary. After 5 failed login attempts from an IP, it's blocked for an exponentially increasing duration (5 min, 15 min, 1 hour). Blocked IPs receive 403 responses before reaching any route logic. The block list is in-memory (resets on restart) — in production I'd persist it to Redis.

How do you prevent path traversal? Strength

Every file path is validated with os.path.abspath() and checked against the configured UPLOAD_FOLDER base. If a resolved path doesn't start with the base directory, it's rejected. Filename sanitization also strips dangerous characters like .., null bytes, and path separators. The storage root is never exposed to user input.

What security headers do you use?

X-Content-Type-Options: nosniff, X-Frame-Options: DENY, X-XSS-Protection, Strict-Transport-Security (when HTTPS is configured), Content-Security-Policy on rendered pages. These are set in the app factory's after_request handler.

Why block certain extensions?

Executable files (.exe, .bat, .sh, .ps1, etc.) could be used to attack other users or the server if accidentally downloaded and run. The extension list is configurable in app/config.py. This is a defense-in-depth measure — the app also validates MIME types and the actual file content.

How secure are public share links?

Share tokens are generated with secrets.token_urlsafe(32) — 256 bits of entropy, cryptographically random, not guessable. Password-protected links hash the password with bcrypt. Links can have expiration times and one-time download limits. Each download is logged with IP and timestamp. The token URL space is astronomically large.

How are share tokens generated?

secrets.token_urlsafe(32) from Python's standard library. This uses the OS's CSPRNG (Cryptographically Secure Pseudo-Random Number Generator) — /dev/urandom on Unix, CryptGenRandom on Windows. URL-safe base64 encoding means no problematic characters. The resulting string is ~43 characters long with 256 bits of entropy.

How do password-protected links work?

When a share link is created with a password, the password is hashed with bcrypt and stored alongside the link. When a visitor accesses the share page, if a password is set, they must submit it. The backend verifies the bcrypt hash before allowing access. The original password is never stored in plaintext.

What are the biggest security weaknesses currently? Weakness

1. No encryption at rest — files are stored as plaintext on disk.
2. No antivirus scanning — blocked extensions help but actual malware detection is absent.
3. No 2FA — password-only authentication.
4. IP blocking is in-memory — doesn't survive restarts, doesn't scale across instances.
5. No formal penetration testing — security relies on code review and static analysis.

How would you implement 2FA? Future

Add a totp_secret column to the User model. Use pyotp to generate TOTP secrets and verify codes. During setup, show a QR code (via qrcode library) for Authenticator apps. On login, after password verification, prompt for the TOTP code. Store backup codes hashed with bcrypt. Add 2FA enable/disable in user settings.

How would you add encryption at rest? Future

Use Fernet (AES-128 in CBC mode with HMAC) from the cryptography library. On upload, encrypt file contents before writing to disk. On download/preview/stream, decrypt on the fly. The tricky part is key management — options: per-user keys derived from passwords (lose password = lose data), or a server master key stored in a secure enclave/HSM. For streaming large files, encrypt in chunks to avoid loading everything into memory.

How would you safely implement antivirus scanning? Future

Install ClamAV daemon (clamd) on the server. After an upload completes, call clamdscan via subprocess or use a Python clamd client over its TCP socket. If a virus is detected, quarantine the file (move to a quarantine directory), notify the user, and log the event. Never execute uploaded files during scanning — ClamAV reads file bytes safely. Run scans asynchronously so uploads aren't blocked.

What penetration testing have you done? Weakness

None formally. Security measures were implemented based on OWASP guidelines and common attack vectors: CSRF, XSS, SQL injection (ORM parameterized queries prevent this), path traversal, brute force, and insecure file uploads. For a production product, I'd hire a third-party penetration testing firm and run tools like OWASP ZAP and Burp Suite.

How would you protect against malicious uploads? Future

Beyond extension blocking: validate MIME type against file content (magic number checking with python-magic), scan with ClamAV, run files in a sandbox for analysis, and restrict preview execution (serve files with Content-Disposition: attachment for untrusted types). Store untrusted files in a separate quarantine area until cleared.

How would you secure this behind HTTPS?

Put Nginx or Caddy in front as a reverse proxy with a Let's Encrypt certificate. Enable HSTS headers. Set SESSION_COOKIE_SECURE=True and SESSION_COOKIE_SAMESITE=Lax in the app config. Redirect all HTTP to HTTPS. Use strong TLS cipher suites. Caddy is actually easier than Nginx for automatic HTTPS — single binary, auto-renews certs.

What happens if SECRET_KEY changes? Strength

All existing sessions become invalid because the session cookie signature no longer verifies. Users are logged out and must re-authenticate. This is by design — rotating secrets forces session invalidation. The app reads SECRET_KEY from .env and warns if it's not set (generating a random key on each startup would break sessions on every restart).

4. File Handling & Storage ▼
How are files stored on disk?

Files are stored in files/users/<user_id>/<filename>. The original filename is preserved for display, but the stored filename is a sanitized version. A database record in the File model tracks metadata (original name, size, MIME type, path, upload date). Shared files are also accessible via files/shared/ for group sharing.

Why organize storage by user ID?

Simplifies quota calculations, permission checks, and cleanup. When a user is deleted, their entire directory tree can be removed. It also prevents filename collisions between users. The tradeoff is that shared/group files need separate handling.

How do uploads work internally? Strength

Flask receives the multipart form upload and streams it to disk in 4MB chunks (UPLOAD_CHUNK_SIZE in config). Before writing, it checks: file size against quota, extension against blocked list, and available disk space. After storage, a database record is created and an activity log is written. The frontend shows real-time progress via XMLHttpRequest's onprogress event.

How do downloads stream files? Strength

For large files, instead of loading the entire file into memory with send_file, the backend uses Flask's streaming response with send_from_directory or a generator that yields chunks. Per-role speed throttling is implemented by sleeping between chunk reads to limit throughput.

How does video streaming work? Strength

HTTP range requests. When a video player seeks, it sends a Range: bytes=start-end header. The backend parses the range, opens the file, seeks to the start position, and streams only the requested bytes with 206 Partial Content status. Multiple ranges per request are also supported. This allows seeking in multi-GB files without loading them entirely.

Explain HTTP range requests.

HTTP range requests let a client request a specific byte range of a resource instead of the entire file. The client sends Range: bytes=0-1023. The server responds with 206 Partial Content, Content-Range: bytes 0-1023/total, and the requested bytes. For video, browsers automatically use range requests when the server advertises Accept-Ranges: bytes. This is essential for video seeking and resuming interrupted downloads.

How do file previews work?

The backend detects the file type from MIME/extension and returns appropriate metadata. Images are served directly. PDFs use browser rendering. Videos and audio use the HTML5 player with streaming endpoints. Text files are read and returned as UTF-8 strings. The frontend component picks a preview renderer based on the file category returned by the API.

How do you prevent huge memory usage during uploads? Strength

Server-side chunked reading — Flask's request stream is consumed in 4MB chunks and written directly to disk. The entire file is never held in memory. For downloads, the same chunking applies — read from disk in segments and yield to the response. This means a 20 GB upload uses the same memory as a 1 KB upload.

How does versioning work? Strength

When a file is updated with the same name, the old file is moved to a versions subdirectory (files/users/<id>/versions/<file_id>/) with a timestamped filename. A FileVersion record tracks the version number, path, size, and timestamp. Users can view version history, restore any previous version (which becomes the current file), or delete old versions to free space.

How are deleted files handled? Strength

Soft delete via a DELETED system tag. The physical file is moved from files/users/ to files/trash/ and a TrashedFile record is created with the original path, deletion timestamp, and scheduled purge date (30 days). The file is excluded from quota calculations. Users can restore (moves file back, removes tag) or permanently delete (removes file and all related records).

Why soft delete instead of permanent delete?

User safety — accidental deletions are recoverable. It also enables the trash view where users can review what they're about to permanently lose. The retention period (30 days) gives a reasonable window without becoming permanent storage. This pattern is standard across all major cloud storage providers.

How does the trash retention scheduler work?

A background thread (Python threading) runs cleanup tasks every 6 hours. It queries TrashedFile records where deleted_at + 30 days < now, permanently deletes the physical files, removes associated ShareLinks and FileVersions, and deletes the database records. The scheduler also handles demo account cleanup every 24 hours.

How would you implement resumable uploads? Future

I'd use the tus protocol (open standard for resumable uploads). The backend would track upload progress in Redis or the database: file ID, total size, received chunks, and temporary storage path. The frontend sends chunks with Offset headers. If interrupted, the client asks the server "how much do you have?" and resumes from there. On completion, chunks are assembled into the final file.

How would you support S3/object storage? Future

First, abstract file operations behind an interface: StorageBackend with methods store(), retrieve(), delete(), stream(), exists(). Implement LocalStorageBackend (current behavior) and S3StorageBackend using boto3. Configure via environment variable. For S3, uploads go directly to a bucket with a key like users/{user_id}/{file_id}. Pre-signed URLs handle downloads without proxying through Flask. For video streaming, S3 supports range requests natively.

How would you handle millions of files? Future

Millions of files in one directory is a filesystem nightmare. Solutions: shard by user ID hash into subdirectories (like files/users/ab/cd/abcdef...), use a flat object store (S3 handles this natively), or maintain a metadata database and use a content-addressed store (hash the file contents as the key). Database side: add indexes on user_id + uploaded_at, paginate aggressively, and use materialized views for statistics.

What are the filesystem limitations?

NTFS/ext4 have practical limits around millions of files per directory (slow listing). Maximum file sizes are in the TB range so not a concern. Path length limits (260 chars on Windows) are handled by using short stored filenames while preserving original names in the database. Disk space exhaustion is checked before each upload.

How do you calculate quotas?

Each user has a storage_used integer (bytes) on the User model. On upload, the file size is added. On soft delete, it's subtracted. On permanent delete or version deletion, it adjusts. The user's role defines their storage_limit. The API returns both values so the frontend can show a progress bar. There's a periodic consistency check in case of drift.

How do speed limits work? Strength

Each role has upload_speed_limit and download_speed_limit (KB/s, 0 = unlimited). During file streaming, the backend reads a chunk, yields it, then sleeps for chunk_size / speed_limit seconds. This throttles throughput without dropping connections. It's simple but effective for per-user bandwidth control.

What happens if disk space runs out?

Before each upload, the backend checks available disk space. If insufficient, the upload is rejected with a clear error message. The frontend shows this to the user. For the admin, storage statistics show used vs total. There's no automatic cleanup — admin intervention is required, which is intentional to prevent surprise data loss.

5. Database Questions ▼
Why SQLAlchemy? Strength

SQLAlchemy is the standard Python ORM. It supports SQLite, PostgreSQL, and MySQL through the same model definitions. Its relationship system (one-to-many, many-to-many via association tables) made modeling users, files, tags, groups, and shares straightforward. Flask-SQLAlchemy integration is seamless.

What database schema decisions were important? Strength

1. Association tables for many-to-many: file_tags, user_groups — keeps models normalized.
2. Separate TrashedFile model — not just a flag, because trash needs its own metadata (deleted_at, restore path, retention date).
3. FileVersion as separate table — versions have their own sizes and timestamps, and keeping them independent allows restoring without losing the current file.
4. System tags — the DELETED tag is marked is_system=True so it can't be accidentally deleted by users.
5. Role-based quotas — roles have a storage_limit, not users directly. This means changing a role's limit updates all members instantly without touching every user record.

How are relationships modeled?

Standard SQLAlchemy relationships: User has many Files (one-to-many). File has many Tags via file_tags association table (many-to-many). File has many FileVersions (one-to-many). User has many ShareLinks (one-to-many). User belongs to many Groups via user_groups. ActivityLog has a foreign key to User. Cascade deletes are configured where appropriate.

Why fallback to SQLite automatically? Strength

Resilience. If someone configures PostgreSQL but the container is down, the app shouldn't crash. It logs the connection failure, falls back to SQLite, and continues running. This is implemented in config.py where the database URL is tested at startup and SQLite is used as a catch-all fallback. The user can fix their config and restart later.

What problems can SQLite cause? Weakness

SQLite locks the entire database for writes. Under concurrent uploads from multiple users, one writer blocks all others. It also lacks features like proper ALTER TABLE, full-text search, and advanced indexing. The WAL (Write-Ahead Logging) journal mode helps but doesn't eliminate the fundamental single-writer limitation.

When should users switch to PostgreSQL?

When they have 3+ concurrent users, need high availability, want point-in-time backups, or plan to grow beyond a few thousand files. PostgreSQL handles concurrent writes, supports JSONB for flexible metadata, has excellent full-text search, and tools like pg_dump for backups. The app makes switching easy — just change DATABASE_URL.

How would you optimize slow queries?

Add composite indexes on frequently queried columns: (user_id, uploaded_at) for file listings, (file_id, created_at) for versions. Use EXPLAIN ANALYZE to identify sequential scans. For admin statistics, pre-aggregate counts in a summary table updated by triggers or background jobs instead of counting on every request.

What indexes would you add?

Already have indexes on primary keys and foreign keys (SQLAlchemy creates these automatically). I'd add: CREATE INDEX idx_files_user_uploaded ON files(user_id, uploaded_at DESC) for dashboard loading, idx_trashed_deleted_at ON trashed_files(deleted_at) for scheduler cleanup queries, and idx_share_token ON share_links(token) for public share lookups.

How would you handle database migrations?

Flask-Migrate (Alembic) is already integrated. For each schema change, generate a migration with flask db migrate -m "description", review the autogenerated script, and apply with flask db upgrade. For production, migrations run before the app starts in the deployment pipeline. Backups are taken before any migration.

How would you backup user data?

For SQLite: copy instance/nas.db and the files/ directory. For PostgreSQL: pg_dump the database and rsync the files directory. Automated: cron job that runs nightly, compresses to a timestamped archive, and uploads to a secondary location (S3, another server, or external drive). Test restores periodically.

How do you prevent database corruption?

For SQLite: WAL mode reduces corruption risk, and the app always closes connections properly (Flask-SQLAlchemy's teardown handlers). For PostgreSQL: use transactions for multi-step operations (upload file + create record), validate foreign key constraints, and never run raw DDL in production without backups.

How would you scale the database layer?

PostgreSQL read replicas for read-heavy workloads (file listings, share views). Connection pooling with PgBouncer. Partition large tables (activity logs) by date. Shard by user ID if scaling horizontally. For truly massive scale, consider splitting the metadata database (small, relational) from file metadata (potentially huge, could use a document store).

6. Frontend Questions ▼
How is the React app structured?

Single-page application with 23 components and 5 context providers. Main views: Dashboard (file grid), AdminPanel, FileList, Notes, ThemeSettings, UserProfile. Shared components: UploadIndicator, Modal, Toast notifications, Sidebar/Navbar. State management uses React Context — no Redux needed for this scale. The upload system is the most complex: a floating drag-and-drop indicator with real-time progress across multiple concurrent uploads.

Why use Vite?

Vite is significantly faster than Create React App for development (native ESM, no bundling during dev) and produces smaller production builds (Rollup with tree-shaking). Hot Module Replacement is near-instant. The config is minimal — the project just needs React, a build output directory, and proxy settings for API calls during development.

How do you manage themes? Strength

CSS custom properties (variables) defined in a base stylesheet. ThemeContext stores the current color values and applies them by updating CSS variables on the document root. Themes are persisted to localStorage. Users can customize 10+ color variables with a live preview. Themes can be exported/imported as JSON. Dark/light mode toggles a class on the HTML element that switches the variable definitions.

How does live updating work? Strength

The Dashboard auto-polls the file list API every 15 seconds. During active uploads, polling increases to 5 seconds. A silent fetch function updates state without showing loading skeletons, so the UI feels live without jarring refreshes. The UploadContext tracks lastCompletedAt — when an upload finishes, the Dashboard immediately refreshes. Storage info also refreshes on window focus.

Why polling instead of WebSockets? Weakness

Polling is simpler to implement, works through firewalls and proxies without configuration, and doesn't require persistent connections. For a personal NAS where the user is typically the only active user, polling every 15 seconds is acceptable. The tradeoff is higher latency (up to 15s before seeing someone else's changes) and unnecessary server load. WebSockets would be the next improvement.

How would you implement WebSockets? Future

Flask-SocketIO on the backend with an async mode (eventlet or gevent). On the frontend, socket.io-client. Events: file_uploaded, file_deleted, share_created. The Dashboard listens and refreshes data on relevant events instead of polling. For auth, pass the session cookie or a JWT in the connection handshake. Fallback to polling for clients that can't use WebSockets.

How do you handle large file upload UX? Strength

Drag-and-drop zone on the dashboard, plus a floating UploadIndicator that snaps to screen corners and shows a progress bar per file. Individual file progress is tracked via XMLHttpRequest's onprogress. Completed uploads are shown with success/error states. The indicator is draggable on both mouse and touch devices. Auto-refresh of the file list happens when uploads complete.

How do you manage loading/error states?

Skeleton loaders for the file list and dashboard stats. Toast notifications for actions (upload complete, delete success, error messages). API errors are caught in a central fetch wrapper that shows user-friendly messages. The ModalContext handles confirmation dialogs ("Are you sure you want to delete?"). Loading states are per-component, not global, so parts of the UI remain interactive.

How would you improve frontend performance?

1. Virtualize the file list with react-window for users with thousands of files.
2. Lazy-load route components with React.lazy() and Suspense.
3. Memoize expensive computations with useMemo.
4. Debounce search/filter inputs.
5. Preload critical assets. Image thumbnails instead of full-size previews in the grid.

What accessibility concerns exist? Weakness

The app could use more ARIA labels, keyboard navigation for the file grid, and focus management in modals. Color contrast should be audited against WCAG standards. The drag-and-drop upload zone needs keyboard fallback. Screen reader support for the upload progress indicator is minimal. These are known gaps that would be addressed in a production pass.

7. DevOps & Deployment ▼
How is the app deployed?

Currently manual: clone repo, install dependencies, build frontend, run python run.py. The installers automate this for each platform. For production, Gunicorn (Linux/macOS) or Waitress (Windows) runs multiple worker processes. A reverse proxy (Nginx or Caddy) handles HTTPS, static files, and rate limiting at the edge.

Why Gunicorn/Waitress?

Flask's built-in server is single-threaded and not production-ready. Gunicorn is a pre-fork WSGI server that handles multiple requests concurrently using worker processes. Waitress is the Windows-friendly equivalent — pure Python, no compilation needed, supports multiple threads. Both are battle-tested and simple to configure.

How would you containerize this?

A multi-stage Dockerfile: stage 1 (Node) builds the React frontend, stage 2 (Python) installs dependencies and copies the built static files. The final image runs Gunicorn. Mount volumes for files/ and logs/. Environment variables configure the container at runtime. A docker-compose.yml would orchestrate the app + PostgreSQL + Redis.

How would you deploy this to production?

Option A: Docker Compose on a VPS (Linode, DigitalOcean) with Caddy for HTTPS. Option B: Kubernetes cluster with Helm charts for horizontal scaling. Option C: Platform-as-a-Service (Render, Railway, Fly.io) for zero-devops deployment. For a small team, Option A is ideal — simple, cheap, and fully controlled.

How would you run it behind Nginx/Caddy?

Caddy is easiest: reverse_proxy localhost:8000 and it auto-manages Let's Encrypt certificates. For Nginx: proxy_pass to the Gunicorn socket, serve static files directly, set appropriate headers (X-Forwarded-For, X-Forwarded-Proto), and configure SSL. Both handle connection pooling, compression, and caching better than the app server.

How would you handle automated backups?

Nightly cron job: pg_dump the database, tar the files directory, compress with gzip, upload to S3/Backblaze B2 with timestamped filenames. Keep 7 daily, 4 weekly, and 12 monthly backups. Alert if backup fails. For SQLite, simply copy the .db file (it's safe when the app isn't writing, or use the .backup SQL command).

How would you monitor production health?

Prometheus metrics endpoint for request counts, error rates, response times, and storage usage. Grafana dashboards for visualization. Uptime monitoring with Pingdom or UptimeRobot. Log aggregation to Loki or CloudWatch. Alert on high error rates, disk space thresholds, and failed backup jobs.

How would you collect logs?

Structured JSON logging from the Flask app. Ship logs to an aggregator (ELK stack, Datadog, or simple file tailing to a central server). Include request ID, user ID, endpoint, duration, and status code. Rotate log files to prevent disk exhaustion. The app already writes to logs/nas.log with rotating file handlers.

How would you support rolling updates?

With multiple Gunicorn workers behind a load balancer: drain one instance (stop accepting new connections, wait for active requests to finish), deploy new code, start it, then move to the next. Docker Swarm and Kubernetes handle this natively. Database migrations run before any app instances are updated. For zero-downtime, blue-green deployment: spin up a new environment, switch traffic, then tear down the old.

How would you deploy this on Kubernetes?

Deployments for the app (3+ replicas), StatefulSet for PostgreSQL (with PersistentVolumeClaims), Deployment for Redis. Ingress controller (nginx-ingress) for routing and SSL. Secrets for database credentials and SECRET_KEY. HorizontalPodAutoscaler for CPU-based scaling. Jobs for database migrations and scheduled backups.

How would you handle zero-downtime deploys?

Blue-green: maintain two identical production environments. Route traffic to green, deploy to blue, run health checks, switch the load balancer to blue. If issues arise, instant rollback by switching back. Database changes must be backward-compatible (add columns, never remove — clean up later). This is overkill for a small deployment but essential for SLA-bound products.

8. Performance & Scaling ▼
What are the current bottlenecks? Weakness

1. SQLite concurrency — single writer blocks all others.
2. Polling overhead — every client hits the server every 15s even when nothing changed.
3. No caching — file lists, user stats, and storage info are queried from the database on every request.
4. Single-process file serving — large downloads monopolize a worker thread.
5. No CDN — static assets and file downloads come from the Flask server.

How many users do you think it supports?

With SQLite: 1–3 concurrent users comfortably. With PostgreSQL and Gunicorn (4 workers): 10–20 concurrent users. The real limit is file I/O — if many users are uploading/downloading large files simultaneously, disk bandwidth becomes the bottleneck before the application layer.

What happens under heavy concurrent uploads?

With SQLite, writes queue up and requests may timeout. With PostgreSQL, uploads proceed concurrently but disk I/O on a single server will eventually saturate. The upload speed throttling helps prevent any single user from monopolizing bandwidth. Chunked server-side reads prevent memory exhaustion.

What happens under heavy streaming traffic?

Each video stream holds a worker process/thread open. With Gunicorn's sync workers, a 4-worker setup can handle 4 concurrent streams. Switch to gevent/async workers for higher concurrency. For many concurrent streams, offloading to a dedicated media server or CDN is the right solution.

How would you benchmark performance?

Use locust or k6 to simulate concurrent users: log in, list files, upload a test file, download it, stream a video. Measure p50/p95/p99 response times, throughput (requests/sec), and error rates. Profile the Python app with cProfile to find hot paths. Monitor database query counts with SQLAlchemy's echo mode.

How would you reduce polling overhead?

Replace polling with WebSockets or Server-Sent Events. If polling must remain, add cache headers so the server returns 304 Not Modified when data hasn't changed. Implement a "last modified" timestamp per user that the client sends — if unchanged, return an empty response instantly.

How would you cache expensive operations?

Redis for: user storage quotas (invalidate on upload/delete), file list metadata (TTL 30s), and admin statistics (recalculate every minute, not every request). Use Flask-Caching with a Redis backend. Static files are already served with cache headers by the reverse proxy.

How would CDN integration work?

With S3: configure a CloudFront or Cloudflare distribution in front of the bucket. Pre-signed URLs are generated by the backend but served directly from the CDN edge. For the React app, the built static assets (JS, CSS, images) are uploaded to the CDN during deployment. The backend only handles API requests and HTML shell serving.

What are the memory-heavy areas?

PDF generation for admin reports, large CSV exports of activity logs, and preview generation for images (Pillow resizing). These are all optional admin operations. For normal usage, memory is bounded by the 4MB upload/download chunks. The biggest risk is accidentally loading a large file into memory instead of streaming it — prevented by using chunk-based I/O everywhere.

What tasks should become async/background jobs?

Already backgrounded: trash cleanup, demo cleanup. Should also be async: email sending (currently synchronous), file virus scanning, thumbnail generation for previews, storage quota recalculation, and large CSV exports. Celery + Redis would be the standard Python stack for this.

9. Testing & Reliability ▼
What testing have you done? Weakness

Manual testing: upload/download various file types, test share links with passwords/expiration, verify rate limiting by exceeding thresholds, test database fallback by stopping PostgreSQL. No automated test suite exists yet — this is a known gap that would be the first priority for production readiness.

Why / why not automated tests? Weakness

Honestly, time and scope. The project grew organically from a simple file upload demo into a full system. Automated tests weren't prioritized during rapid feature development. For production, I'd add pytest for the backend (using Flask's test client and SQLite in-memory DB) and React Testing Library for the frontend. Integration tests for the upload→trash→restore→delete flow would be critical.

How would you test uploads?

Backend: create test files (empty, 1KB, 1MB, max size, blocked extension, path traversal filename), post to the upload endpoint, verify database record, verify physical file exists, verify quota updated. Test chunked uploads by splitting a file and sending parts. Frontend: simulate drag-and-drop with @testing-library/user-event, verify progress bar updates, verify file appears in the list after completion.

How would you test authentication?

Unit tests for password hashing (bcrypt vs PBKDF2 migration). Integration tests: register with valid/invalid data, login with correct/incorrect credentials, test rate limiting by brute-forcing, verify CSRF rejection without token, test session persistence across requests, test logout clears the session. Test role-based access: verify non-admin can't hit admin endpoints.

How would you test file corruption scenarios?

Upload a file, corrupt the physical file on disk (flip bytes), attempt to download — should still succeed if the corruption is after the verified bytes, or should detect hash mismatch if we implement integrity checks. Test partial upload interruption: kill the request mid-upload, verify no orphaned partial files remain, verify database has no incomplete record.

How would you test concurrent access?

Use threading or locust to hit the same endpoint simultaneously: two users uploading to the same account, two downloads of the same file, one user deleting while another downloads. Verify SQLite handles the locking gracefully (or fails predictably) and PostgreSQL handles true concurrency. Test quota edge cases: simultaneous uploads that together exceed the limit.

How do you debug production issues?

Structured logging with request IDs, user IDs, and timestamps. logs/nas.log has rotating file handlers. For debugging, set FLASK_DEBUG=1 for detailed tracebacks. In production, Sentry integration would capture exceptions with full stack traces. Database query logging reveals N+1 issues.

What was your worst bug? Strength

The foreign key constraint failures when permanently deleting files or users. Deleting a File record would fail because ShareLinks and FileVersions had non-nullable foreign keys to it. The fix required adding cleanup code in every deletion path: trash cleanup, permanent delete, user deletion, and the scheduler. It taught me the importance of thinking through cascade behavior at schema design time, not when production breaks.

What bug taught you the most?

The same FK cascade bug. It taught me that ORM abstractions hide database reality. I now always consider: "What happens to related records when this one is deleted?" before writing any deletion code. It also taught me the value of integration tests that exercise full workflows (upload → share → delete → trash → permanent delete) rather than testing each endpoint in isolation.

How do you reproduce difficult bugs?

Step 1: Check logs for the exact request, user, and timestamp. Step 2: Replicate the database state (what files, tags, and links existed?). Step 3: Step through the code path manually. Step 4: Write a minimal reproduction script that triggers the bug. Once fixed, the script becomes a regression test. For the FK bugs, I created a script that uploaded a file, created a share link, created a version, then deleted the file — this reliably reproduced the crash.

11. Engineering Maturity ▼
What did you learn from this project? [REPLACE WITH YOUR PERSONAL EXPERIENCE]
What would you do differently next time?

Write tests from day one. Even minimal tests would have caught the FK cascade issues early. Design the storage abstraction layer upfront instead of hardcoding local filesystem paths everywhere. Use TypeScript for the frontend — catching prop type errors at build time is worth the setup cost. And start with PostgreSQL in development, not SQLite, to catch concurrency issues early.

How did you manage technical debt?

Refactored as I went: extracted reusable utilities (rate limiting, email, security) from route files, moved inline SQL to model methods, and consolidated duplicate frontend logic into shared hooks. Known debt items are tracked mentally: the polling system, lack of tests, hardcoded storage backend. I fix debt when it blocks a feature or causes bugs.

What feature became more complex than expected?

The trash system. What started as "add a deleted flag" became: moving physical files, tracking restoration paths, handling retention scheduling, adjusting quotas, filtering views, and managing FK constraints on permanent deletion. The soft-delete pattern seems simple but touches almost every subsystem.

How do you decide when code is "good enough"?

Good enough means: it handles the main case, the edge cases I can think of, it has basic error handling, and I can explain how it works to someone else. It's not perfect — there might be missing features or rough UX — but it's reliable and maintainable. I ship when the feature works for the intended use case and move on, returning to polish when user feedback or bugs demand it.

How do you balance perfection vs shipping?

Ship working features, then iterate. The first version of the share system only supported public links — no passwords or expiration. Once that was stable, I added the advanced features. Perfect is the enemy of shipped. However, security and data integrity are non-negotiable — those get thorough review before any release.

What was your biggest architectural mistake?

Not abstracting file storage early. Hardcoding files/users/{user_id}/ paths in 10+ route files means adding S3 support requires touching every file operation. A StorageBackend interface from the start would have made this a config change, not a refactor.

What feature caused cascading complexity?

Multi-user support. Adding users required: authentication, role-based access, storage quotas, admin controls, activity logging, user-specific file paths, and group sharing. Every subsequent feature (sharing, trash, admin dashboard) had to account for which user was performing the action. Single-user would have been much simpler.

How do you prioritize features?

Core workflow first: upload, download, view. Then user management (auth is useless without it). Then quality-of-life: sharing, trash, versioning. Then polish: themes, notes, settings. I ask: "Does this feature make the core experience meaningfully better?" If not, it goes to the backlog.

How would you onboard another developer?

Document the architecture: explain the app factory, blueprints, and data flow. Walk through a complete request lifecycle (upload a file, trace it through routes, models, filesystem). Set up a dev environment with the installer script. Start them on a small, isolated feature (like adding a new file preview type) to learn the patterns. Code review all early PRs for consistency.

Who would realistically pay for it?

Small businesses that need file storage but don't want to pay per-user SaaS fees. Creative professionals with large file storage needs (video editors, photographers). Why would users choose this over Nextcloud?

Simpler setup — no Docker, no PHP, no complex configuration. Better performance on low-end hardware because it's Python + SQLite, not PHP + MySQL. Per-role speed throttling and storage quotas that Nextcloud charges for in the enterprise edition. A modern React UI instead of Nextcloud's older interface. However, Nextcloud has a massive app ecosystem — this is more focused and opinionated.

What are your hosting cost concerns?

Storage is the main cost — users uploading terabytes of video. Bandwidth for downloads and streaming. For a self-hosted product, the user's hardware absorbs this. For a SaaS, I'd need tiered pricing based on storage. Compute is cheap; storage and egress are expensive.

How would you price a hosted version?

Freemium: 5 GB free, $5/month for 100 GB, $15/month for 500 GB, $40/month for 2 TB. Business tier with admin controls, SSO, and audit logs at $10/user/month. The self-hosted version remains a one-time purchase or open-source for personal use. Pricing aligns with AWS S3 + compute costs plus margin.

What legal/privacy concerns exist?

If offering a SaaS: data residency (where are files stored?), encryption requirements, liability for user-uploaded illegal content, terms of service, and DMCA compliance. Self-hosted sidesteps most of these — the user is responsible for their own data. However, the software itself must not facilitate illegal activity (hence the blocked extensions and terms of service requirements).

How would GDPR affect this project?

For a SaaS: need data processing agreements, right to deletion (already supported via user deletion which removes all data), right to export (add a data export feature), privacy policy, and breach notification procedures. For self-hosted: GDPR is the deployer's responsibility, not the software author's. I'd add a data export API to make compliance easier.
